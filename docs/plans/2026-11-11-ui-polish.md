## Verification environment constraint

No system Chrome is installed, so the Playwright / chrome-devtools MCP browsers cannot
launch. Live, logged-in YTM DOM inspection is therefore unavailable this pass. All
verification goes through the Electron app's bundled Chromium:
- `vitest` unit tests (CSS builder, config).
- Playwright `_electron` E2E (`tests/appearance.test.js`) — proves CSS is injected.
- `electron-vite build` + typecheck.

Consequence: pixel-level alignment and any selector that targets *live YTM promo DOM*
cannot be proven here. We therefore (a) make CSS fixes correct by construction, and
(b) reuse already-tested runtime code for cleanup instead of guessing selectors.
Items that need a logged-in live session are explicitly gated, not shipped blind.

## Workstream A — play/pause button alignment (phosphor.css)

Root cause (box model): the rule at `src/appearance/phosphor.css:880` forces
`width/height:34px; padding:4px; border:2px` **without** `box-sizing:border-box`, so the
rendered box is ~46px (content-box) while sibling controls are ~40px, and the inner icon
is neither sized nor re-centered. Result: the bordered box sits proud of its neighbours.

Fix (correct by construction, Phosphor-only, reversible):
- `box-sizing:border-box`, `padding:0`, fixed 36px square, `border-radius:50%`.
- `display:inline-flex; align-items:center; justify-content:center; align-self:center;
  flex:0 0 auto; margin:0` so the box centres on the player-bar cross axis.
- Size the inner `yt-icon`/`iron-icon` to 20px and colour it with the accent.

Verify: build + existing injection E2E (accent `#3f3`). Final pixel confirmation is the
user's visual check (disclosed, not claimed).

## Workstream B — title bar persistence (TitleBar.tsx)

Root cause: `titleStyle` auto-hides the bar in fullscreen
(`ytmusic-app:has(ytmusic-player[player-ui-state='FULLSCREEN']) ~ &:not([data-show='true'])
{ transform: translateY(-height) }`, `src/plugins/in-app-menu/renderer/TitleBar.tsx:60`)
combined with `data-show={mouseY()<32}`. A clean non-test diag already proved the Options
button itself stays visible and its panel opens; the disappearance is the fullscreen
auto-hide, not a broken click handler.

Fix: remove the fullscreen auto-hide transform so the bar is always present. Keep the
drag region and window controls. This guarantees "Options" never vanishes.

Verify: build + typecheck; logic review. (Menu interaction is only exercisable in non-test
mode because the preload bridge is inert under `NODE_ENV=test` — pre-existing, out of scope.)

## Workstream C — safe cleanup (custom + YTM)

Evidence from the live profile (`%APPDATA%/MusicApp/config.json`):
- `options.removeUpgradeButton` is already `true` → the premium upgrade guide entry is
  already hidden by the tested routine at `src/renderer.ts:367`. **No code change needed.**
- `appearance.preset` is `default` → the play-button fix (A) is correctly Phosphor-scoped;
  the default preset uses native YTM styling and is unaffected.

Concrete cleanup shipped:
1. **Remove debug red scrollbar.** `src/plugins/in-app-menu/renderer.tsx` injected
   `html::-webkit-scrollbar { background-color: red; }` — a leftover debug style. Deleted
   the constant and its `adoptedStyleSheets` injection.

Deliberately NOT done blind: an always-on `cleanup.css` of guessed YTM promo selectors, and
making upgrade-removal unconditional. Without a live DOM we cannot prove those selectors are
safe; the existing routine's `:last-child` fallback could hide a legitimate guide entry, so we
keep it gated on the (already-enabled) toggle rather than force it. Any further YTM cleanup
needs the user to name the specific element (gated follow-on).

Verify: build + typecheck; unit/E2E unaffected (no `--tm-accent` change).

## Workstream D — unify settings into YTM's own settings (GATED)

Goal: surface MusicApp options (appearance preset, plugin toggles) inside YTM's native
settings dialog instead of only the custom menu.

Risk: YTM's settings dialog is a Polymer `tp-yt-paper-dialog` with dynamic content; injecting
a durable section requires a MutationObserver + IPC and breaks on YTM updates. It cannot be
verified without a logged-in live session, which is unavailable this pass.

Decision: design it here, but implement as a separate gated increment once a live session is
available. Do NOT ship fragile, unverified DOM injection. Interim: the custom menu remains the
source of truth; Workstream B keeps it reliably reachable.

## Workstream E — optimization / lean shell

Findings (evidence-based, no unverified perf claims):
- **Runtime is already lean.** `loadAllRendererPlugins` only starts a plugin when
  `config.enabled` (`src/loader/renderer.ts:121`). Plugins are lazy dynamic imports
  (`vite-plugins/plugin-importer.mts:54`), so disabled plugins are never evaluated.
- **Default-enabled set is small and beneficial:** the 6 curated brand plugins
  (`brand-plugin-defaults.ts`) plus `performance-improvement` (the only other plugin whose
  def config is `enabled:true`), which injects `cpu-tamer` + `rm3` rendering optimisations.
  No heavy plugin is enabled by default.
- **Bundle is one 6.5MB IIFE** (`dist/renderer/musicapp.iife.js`). The renderer build is
  `formats:['iife']` (`electron.vite.config.mts:118`), which cannot code-split, so every
  plugin's code is inlined even though only enabled ones run. Parse cost is paid at startup.

Conclusion: there is no safe, polish-level code change that measurably improves this — the
runtime is already gated and the performance plugin is active. The real lever is switching the
renderer injection from IIFE to ES modules with code-splitting so disabled plugins are not
downloaded/parsed. That changes the injection architecture and is a separate, riskier effort —
gated, not shipped blind. No "faster" claim is made without a measured baseline.
